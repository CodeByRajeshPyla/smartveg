## 1. Packages

Flutter does not know how to talk Bluetooth. Nobody writes that from scratch — you add a
**package**: code someone else wrote and published. Flutter's package library is
**pub.dev**. This project uses **`flutter_blue_plus`** (decided in `01_PROJECT_CONTEXT.md`).

### `pubspec.yaml` = the project's shopping list of packages

```yaml
dependencies:
  flutter:
    sdk: flutter
  cupertino_icons: ^1.0.8
  flutter_blue_plus: ^2.3.14      # added in this lesson
```

### Adding one
```
flutter pub add flutter_blue_plus
```
Does two things: writes the line into `pubspec.yaml` with a suitable version, **and**
downloads the package. (Older way: type the line by hand, then run `flutter pub get`.)

### Version syntax — the caret
**`^2.3.14`** = version 2.3.14 or any newer **compatible** version — newer `2.x`, but
**never `3.0`**. A major-version change may break your code, so the caret refuses it.

### YAML rules (the format of pubspec.yaml — not Dart)
- **Indentation is meaning.** A line indented under `dependencies:` belongs to it. Wrong
  indentation = broken file.
- **Spaces only, never tabs.**

## 2. Why a package can need a FULL rebuild

`flutter_blue_plus` contains **native Android code** (Kotlin/Java that talks to the
Bluetooth radio). Hot reload and hot restart only swap **Dart** code; native code is
compiled into the app at install time.

> Three levels of change: **`r`** reload (Dart UI) · **`R`** restart (`main()`,
> packages' Dart side, starting values) · **full rebuild** — `q` then `flutter run` —
> for anything native: manifest changes, packages with native code.

## 3. Permissions — two separate steps

| Step | What | Where | When |
|---|---|---|---|
| **Declare** | the app lists what it *may* ask for | `AndroidManifest.xml` | when the app is built — **this lesson** |
| **Request** | the app asks the **user**: *"Allow SmartVeg to find nearby devices?"* | Dart code | while the app runs — **F2.2** |

Both are between **the app and the phone's owner** — no other device is involved.

**Declaring alone grants nothing.** It only makes asking *possible*. Without the
declaration the request is silently refused and no popup ever appears.

### Seen on the phone
After a full rebuild: **Settings -> Apps -> vegbill -> Permissions** showed
**"Nearby devices: Not allowed"**. It was not listed before. *Not allowed* because
nobody has asked yet.

## 4. The five permission lines

In `android/app/src/main/AndroidManifest.xml`, **inside `<manifest>`, before
`<application>`** — permissions belong to the whole app, not one screen.

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
    <uses-permission android:name="android.permission.BLUETOOTH_SCAN"
        android:usesPermissionFlags="neverForLocation" />
    <uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" android:maxSdkVersion="30" />
    <uses-permission android:name="android.permission.BLUETOOTH" android:maxSdkVersion="30" />
    <uses-permission android:name="android.permission.BLUETOOTH_ADMIN" android:maxSdkVersion="30" />

    <application ...
```

### They are two sets
| Phone | Permissions used | Job |
|---|---|---|
| **Android 12+** (this phone is 14) | `BLUETOOTH_SCAN` | **search** for nearby devices — find "ESP32-Scale" |
| | `BLUETOOTH_CONNECT` | **connect** and exchange data — receive `"1486.0,1"` |
| **Android 11 and older** | `BLUETOOTH`, `BLUETOOTH_ADMIN` | the old versions of scan + connect. Android split and renamed them in version 12. |
| | `ACCESS_FINE_LOCATION` | old phones demanded location for scanning (section 5) |

**`android:maxSdkVersion="30"`** = apply only on Android 11 (API 30) or older. On an
Android 14 phone these three lines are ignored.

**Why keep the old set at all:** a vegetable vendor could easily have a cheap old phone.

### XML rules (the format of the manifest)
- Every tag is `<name ... />` or `<name> ... </name>`.
- **`/>` = self-closing** — the tag has nothing inside. Missing it breaks the file.
- XML ignores indentation, but keep it tidy: **Shift+Alt+F** formats the file in VS Code.

## 5. THE VIVA QUESTION — why location permission for Bluetooth?

Shopping malls, airports and shops have small **Bluetooth beacons** fixed to their walls.
Each broadcasts an ID, and **its position is known**. An app that scans and sees
"beacon #4471 is nearby" can look up where you are standing — to within a few metres,
indoors, with no GPS.

> **Because Bluetooth beacons have known positions, a Bluetooth scan can reveal your
> location, so Android treats scanning as location access and requires location
> permission.**

It is **not** about Bluetooth's range.

### What Android 12+ changed
Google separated the two. **`BLUETOOTH_SCAN` with `neverForLocation`** is the app
*promising* it will not use scan results to locate the user — so no location permission
is needed. That is the flag on line 3.

**Q: What is `pubspec.yaml` for, and what does `^2.3.14` mean?**
It lists the packages the project depends on. `^2.3.14` accepts 2.3.14 or any newer 2.x,
but never 3.0.

**Q: Why did the package need a full rebuild?**
It contains native Android code, which is compiled in at install time; `r` and `R` only
swap Dart code.

**Q: Declare vs request?**
Declare = list the permission in AndroidManifest.xml at build time. Request = ask the user
for it at run time with a popup. Declaring alone grants nothing.

**Q: Why did old Android need location permission for Bluetooth scanning?**
Beacons have known positions, so a scan can reveal where the phone is; Android therefore
treated scanning as location access.
