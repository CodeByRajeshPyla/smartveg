## 1. The one idea

> **In Flutter you don't change the screen. You change the data, and `build()` redraws
> the screen from it.**

Every screen in the project works this way. The Weigh screen will not "update the weight
label" — it will change a weight variable and let `build()` redraw.

### `const` meets state
```dart
const Column( ... LinearProgressIndicator(value: _progress) ... )   // ERROR
```
`const` means *built once at compile time, never changes*. A variable that changes cannot
live inside it.
> **The moment something depends on state, it cannot be `const` — and neither can
> anything containing it.**

## 3. `setState` — what it does

> **`setState(() { ... })` runs your code, then tells Flutter "my data changed — call
> `build()` again."**

Two things, every call:
1. runs the code inside it — `_ticks = _ticks + 1`
2. notifies Flutter that a rebuild is needed

Do not confuse the three: the **Timer** ticks every second -> it calls **`setState`** ->
`setState` causes **`build`**.

### The "break it" experiment (done first, deliberately)
Timer changing the variable **without** `setState`:
- **terminal** (via `print`): `0.1, 0.2, 0.30000000000000004 ...` — the variable WAS changing
- **phone**: bar frozen at zero — the screen was NOT changing

> **Changing a variable does not redraw the screen. Flutter only redraws when told to.**

## 4. How `setState` reaches `build` — there is a middleman

In your own code no line connects them. The link is inside Flutter
(`D:\flutterr\flutter\packages\flutter\lib\src\widgets\framework.dart`):

| Line | Code | Does |
|---|---|---|
| 1160 | `void setState(VoidCallback fn)` | runs your `fn()` ... |
| 1219 | `_element!.markNeedsBuild();` | ... then only *marks* the screen. It does not build. |
| 5392 | `_dirty = true;` | flags the screen as **dirty** |
| 5393 | `owner!.scheduleBuildFor(this);` | puts it on a **to-do list** |
| 5820 | `built = build();` | on the next frame (~60/sec), Flutter calls **your `build()`** |

```
Timer ticks
  -> setState(() { _ticks++ })     your code changes the data
  -> markNeedsBuild()              Flutter: "this screen is dirty"
  -> to-do list                    waits for the next frame (~16 ms)
  -> build()                       Flutter redraws from the new data
```

**Why it is called `setState`, not `rebuild`:** you are announcing "my state is set",
and Flutter decides when to draw.

**Why the middleman:** call `setState` five times in a row and the screen is only marked
dirty five times — Flutter still draws **once** on the next frame.

**Bonus from the source:** the first check inside `setState` is
`_debugLifecycleState == _StateLifecycle.defunct` — *defunct* means `dispose()` has
already run. That is the check that throws `setState() called after dispose()`.

## 5. The State lifecycle — the three methods

```
screen opens                                            screen closes
    |                                                         |
initState()   ONCE                                       dispose()   ONCE
    |                                                         ^
build()  build()  build()  ...  build()                       |
 first   after    after         after                         |
 draw    tick 1   tick 2        tick 10                (next screen opens)
```

| Method | Called by Flutter when | How many times | Job | Splash |
|---|---|---|---|---|
| **`initState()`** | the screen is **born** | **once** | **start** things | start the timer |
| **`build()`** | the screen must be drawn | **many** — once at start + once per `setState` | **draw** from current data | draw the bar at `_ticks / 10` |
| **`dispose()`** | the screen **dies** | **once** | **stop** what `initState` started | cancel the timer |

**You never call these. Flutter does.**

### Measured, not assumed
With a `print` in each: in 10 seconds `initState` printed **once**, `build` printed
**11 times** (1 first draw + 10 `setState`s).

### Why each thing goes where it goes
| Placement | Result |
|---|---|
| Timer in `build` | WRONG — 11 builds = 11 timers all ticking |
| Timer in `initState` | RIGHT — one timer |
| Cancel in `build` | WRONG — cancelled on the first redraw, bar stops at tick 1 |
| Cancel in `dispose` | RIGHT — once, at the end |

> **`initState` and `dispose` are a pair: whatever you start in one, stop in the other.
> `build` only draws — it never starts or stops anything.**

Shop analogy: `initState` = unlock and switch on the lights · `build` = serve each
customer · `dispose` = switch off and lock up. Open once, serve many, close once.

### Where this pattern recurs in the project
| Where | Started in `initState` | Stopped in `dispose` |
|---|---|---|
| Splash (now) | Timer | `_timer?.cancel()` |
| Stage 2 — Weigh screen | listening to the **Bluetooth weight stream** | stop listening |
| Stage 5 — forms | text input controllers | release them |

Weigh screen: listening **starts** in `initState`, **stops** in `dispose`, the weight is
**shown** in `build`.

## 6. The code

```dart
import 'package:flutter/material.dart';
import 'dart:async';

class _SplashScreenState extends State<SplashScreen> {
  int _ticks = 0;
  Timer? _timer;

  @override
  void initState() {
    super.initState();                       // super FIRST: Flutter sets up, then you
    _timer = Timer.periodic(const Duration(seconds: 1), (timer) {
      setState(() {
        _ticks = _ticks + 1;
      });
      if (_ticks >= 10) {
        timer.cancel();
      }
    });
  }

  @override
  void dispose() {
    _timer?.cancel();
    super.dispose();                         // super LAST: you clean up, then Flutter
  }

  @override
  Widget build(BuildContext context) { ... }
}
```

- **State variables go in the class body, not inside `build()`** — inside `build` they
  would be recreated and reset on every rebuild.
- `timer.cancel()` — the `timer` parameter Flutter passes in *is* the Timer, so it can
  cancel itself.
- The Timer is stored in `_timer` only so `dispose()` can reach it.

## 7. int, not double — and why it matters for money

`0.1` cannot be stored exactly in binary. Ten additions give:
```
0.9999999999999999        not 1.0
```
So `if (_progress >= 1.0)` missed at tick 10 and the timer ran one tick too long.
The terminal also showed `0.30000000000000004`.

**Fix: count in whole numbers, divide only when drawing.**
```dart
int _ticks = 0;                              // 0, 1, 2 ... 10 — exact
LinearProgressIndicator(value: _ticks / 10)  // int / int gives a double, at draw time
```

**The project rule this is:** `01_PROJECT_CONTEXT.md` — *"money math must be exact (no
floating-point rounding bugs on prices)"*. With `double` rupees, `0.10 + 0.20` gives
`0.30000000000000004`. In Stage 3 prices are stored as **paise in an `int`** (`9687`) and
divided by 100 only to *show* `Rs 96.87`.

## 8. DART CONCEPTS USED HERE

| Feature | Syntax | Meaning |
|---|---|---|
| core library import | `import 'dart:async';` | `dart:` = part of Dart itself, not a package. `Timer` lives here. |
| anonymous function | `(timer) { ... }` | a function with no name, passed as an argument; Timer calls it each tick |
| string interpolation | `'ticks = $_ticks'` | `$name` inserts a variable's value |
| `Duration` | `const Duration(seconds: 1)` | a length of time; also `milliseconds:`, `minutes:` |
| nullable type | `Timer? _timer;` | `?` = may be `null`. It *is* null until `initState` assigns it |
| null-aware call | `_timer?.cancel();` | call only if not null, otherwise do nothing. A method on `null` crashes |
| ternary operator | `cond ? a : b` | an if/else that **produces a value**, so it can sit inside a widget |
| int division | `3 / 10` | `/` on two ints gives a `double` (`0.3`). `~/` gives an int |

## 9. Problems hit, and what each taught

| Symptom | Cause | Lesson |

| Changed `_progress = 0.3`, pressed `r`, nothing | **hot reload keeps State**, so the starting value of a state variable never re-runs | press **`R`** after changing a state variable's starting value |

## 10. GATE — PASSED

**Q: What does `setState` do?** Runs the code inside it, then tells Flutter the data
changed so `build()` is called again.

**Q: What broke without it?** The terminal showed the variable increasing every second,
but the bar on the phone stayed at zero — the data changed, the screen did not.

**Q: Why the timer in `initState`, not `build`?** `initState` runs once; `build` ran 11
times. A timer in `build` would start a new timer on every rebuild.

**Q: Why `int` and not `double`?** `0.1` added ten times gives `0.9999999999999999`,
not `1.0`; an int count is exact. Same reason money is stored as paise in an `int`.

**Q: What is `dispose()` for?** Runs once when the screen is destroyed, to stop whatever
`initState` started.

**Q: Weigh screen — start / show / stop?** `initState` / `build` / `dispose`.
