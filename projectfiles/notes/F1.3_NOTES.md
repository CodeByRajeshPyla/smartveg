# F1.3 — Stateless vs Stateful

Course: 03_FLUTTER_COURSE.md · Screen 01 (Splash) · **STATUS: GATE PASSED**

---

## 1. The distinction

> **Stateless** = drawn once, never changes.
> **Stateful** = holds data that changes over time, and can ask Flutter to redraw.

### The test to apply every time
> **Does anything on this screen change after it is first drawn, while the user is
> still on it?**
> No -> stateless. Yes -> stateful.

Not "will I add features later" — the question is about change *during* the screen's life.

| Screen | Why |
|---|---|
| Splash | **stateful** — the progress bar fills |
| Weigh & Select | **stateful** — live weight streams in |
| Cart | **stateful** — items added and removed |
| A static label, icon, header | **stateless** |

**Default to stateless.** Simpler, cheaper, easier to reason about. Reach for stateful
only when something genuinely changes.

## 2. Why a StatefulWidget is TWO classes

### The fact most people do not know: `build()` runs over and over
`build()` does not run once. **Flutter calls it again every time anything needs to
change on screen** — for a progress bar updating 20 times a second, `build()` runs 20
times a second.

Each time, Flutter **creates brand-new widget objects and throws the old ones away**.
`Container`, `Text`, `Column` are cheap *descriptions*, not real things on screen.

### The problem this causes
If the changing number lived in the widget:

```dart
class SplashScreen extends StatefulWidget {
  double progress = 0.0;        // if it lived HERE
}
```

```
progress = 0.2 -> something changes -> Flutter rebuilds
                                    -> OLD widget thrown away
                                    -> NEW widget created
                                    -> progress = 0.0 again   WRONG
```

The bar would be stuck at zero forever. The widget was destroyed and the data went with it.

### The fix

```
SplashScreen          <- the widget. THROWN AWAY and recreated constantly.
_SplashScreenState    <- the State. CREATED ONCE, kept alive by Flutter.
```

Flutter holds the State object. On rebuild it reconnects the **new** widget to the
**same old** State:

```
progress = 0.2 -> rebuild -> new SplashScreen widget
                          -> SAME _SplashScreenState
                          -> progress still 0.2   CORRECT
```

| Class | Lifetime | Holds |
|---|---|---|
| `SplashScreen` (widget) | **disposable**, recreated constantly | configuration passed in |
| `_SplashScreenState` | **persists** across rebuilds | the data that changes, and `build()` |

**That is why `build()` moved into the State class** — `build()` needs the data, and the
data lives in State.

### Viva one-liner
> **The widget is disposable and rebuilt constantly; the State object persists across
> rebuilds and holds the data that changes.**

## 3. The pattern

```dart
class SplashScreen extends StatefulWidget {
  const SplashScreen({super.key});

  @override
  State<SplashScreen> createState() => _SplashScreenState();
}

class _SplashScreenState extends State<SplashScreen> {
  @override
  Widget build(BuildContext context) {
    return Scaffold( ... );
  }
}
```

`createState()` is Flutter asking "what State object goes with this widget?" You hand it
one. **You never call it yourself.**

## 4. DART CONCEPTS USED HERE

| Feature | Syntax | What it does |
|---|---|---|
| **Inheritance** | `class A extends B { }` | A **is a** B and inherits everything it defines. How every custom widget is made — never from scratch, always by extending Flutter's. |
| **Annotation** | `@override` | "I am deliberately replacing a method my parent defines." Optional, but catches typos — misspell `build` without it and you get an unused method and a blank screen. |
| **Generics** | `State<SplashScreen>` | A **type parameter**, same idea as `List<String>` or `Map<String, int>`. Means "a State belonging to a SplashScreen" — what makes `widget.something` type-safe inside the state. |
| **Arrow syntax** | `Type f() => expression;` | Shorthand for a body that is a **single expression**; `=>` implies the `return`. No `if`, no multiple statements. Long form: `Type f() { return expression; }` |
| **Privacy** | `_name` | Dart has no `private` keyword. **A leading underscore makes an identifier private to its FILE** (not its class). Works on classes, variables, methods. |
| **Named parameters** | `const X({super.key})` | `{...}` = called by name, `X(key: ...)`, not by position. Why Flutter is written `width: 120, height: 120`. |
| **`const` constructor** | `const X(...)` | The object can be built at compile time when its arguments are constant — so Flutter can skip rebuilding it. **Use `const` wherever the analyser suggests it: free performance.** |
| **Super parameter** | `super.key` | Dart 2.17+. "Take `key` and pass it straight to the parent constructor." Old form seen in tutorials: `X({Key? key}) : super(key: key);` |

### Imports and multi-file projects

```dart
import 'package:flutter/material.dart';   // external package
import 'splash_screen.dart';              // own file — plain relative path, no package:
```

- **Each file needs its own imports.** A second file does not inherit `material.dart`
  from `main.dart`.
- **Privacy is per-file**, so `_SplashScreenState` must live in the same file as
  `SplashScreen`. `main.dart` can see `SplashScreen` but never `_SplashScreenState` —
  which is correct, nothing outside should touch it.

### Dart naming conventions (the analyser enforces these)
| Thing | Convention |
|---|---|
| classes / types | `UpperCamelCase` |
| variables / functions | `lowerCamelCase` |
| files | `lowercase_with_underscores` |

## 5. Splitting into files

One screen per file is what real Flutter projects do. The end state here will be
`splash_screen.dart`, `weigh_screen.dart`, `cart_screen.dart` ... instead of a
3000-line `main.dart`.

`main.dart` becomes just the app wrapper:

```dart
return const MaterialApp(
  title: 'SmartVeg',
  home: SplashScreen(),
);
```

> **A refactor that changes the appearance is a refactor that went wrong.** The screen
> must look identical afterwards — same tree, better organised.

## 6. READING ANALYSER ERRORS — the real lesson of this session

16 issues were reported. **Only three were real typos.**

> **One broken character confuses the parser, and it then misreads everything after it.
> Always fix the FIRST error and re-run. Never try to fix all 16.**

| Error | Cause | Fix |
|---|---|---|
| `Methods must have an explicit list of parameters` | `createState` written with no `()` | a method needs `()` even when it takes nothing — that is what distinguishes a method from a variable |
| `A class declaration must have a body, even if it is empty` | `State<Spalshscreen{` — the **`>` was missing**, so Dart lost track completely | close the generic: `State<SplashScreen> {` — **this one error produced most of the other 15** |
| `Expected to find ';'` | the `return Scaffold(...)` closed with `,` | **a `return` statement ends with `;`**. Commas separate items *inside* an argument list; a semicolon ends the statement. |

`info` and `warning` lines are advice, not failures — e.g.
`The type name '_spalshscreenstate' isn't an UpperCamelCase identifier`.

## 7. GATE — PASSED

**Q: When do you need Stateful?** When something on the screen changes after it is first
drawn, while the user is still on it.

**Q: Why two classes?** Flutter destroys and recreates widgets constantly. Data kept in
the widget would reset on every rebuild, so the changing data lives in a State object
that Flutter keeps alive across rebuilds.

**Q: What is `=>`?** Shorthand for a single-expression function body; it implies the
`return`.

**Q: What does `<SplashScreen>` mean in `State<SplashScreen>`?** A generic type
parameter — this State belongs to a SplashScreen.

**Q: Why the leading underscore?** It makes the class private to its file.
