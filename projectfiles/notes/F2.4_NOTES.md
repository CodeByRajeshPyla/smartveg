## 1. A widget I made myself, with inputs

Until now I only *used* widgets: `Text('hi')`, `Container(width: 120)`. Now I *made*
one — `WeightBar` — in its own file, `lib/weight_bar.dart`. Like `Text`, it takes inputs:

```dart
WeightBar(grams: 503.0, isStable: false, onTare: () { ... })
```

**Why a separate widget:**
- the **Weigh screen** (built later) needs the same panel — reuse, not copy-paste
- the splash file stays short and readable

### How it is written
```dart
class WeightBar extends StatelessWidget {
  const WeightBar({
    super.key,
    required this.grams,
    required this.isStable,
    required this.onTare,
  });

  final double grams;
  final bool isStable;
  final VoidCallback onTare;

  @override
  Widget build(BuildContext context) { ... uses grams, isStable, onTare ... }
}
```

| Part | Meaning |
|---|---|
| `final double grams;` | the widget's inputs are stored in **`final` fields** — set once when created |
| `required this.grams` | a **named** parameter that **must** be given; `this.grams` stores it straight into the field |
| `final VoidCallback onTare;` | an input that is a **function** — what to do when the button is tapped |

### Why it can be Stateless when the weight changes
`WeightBar` does **not** own the weight. The **splash screen's State** holds `_grams` and
calls `setState`. Each `setState` re-runs the splash's `build()`, which creates a
**new** `WeightBar(grams: _grams, ...)` with the new number.

> **A Stateless widget never changes itself — it is re-created with new inputs by the
> parent that owns the state.** Data flows **down** through constructor parameters.

### Used in the splash
```dart
import 'weight_bar.dart';
...
const SizedBox(height: 24),
Padding(
  padding: const EdgeInsets.symmetric(horizontal: 16),
  child: WeightBar(
    grams: _grams,
    isStable: _isStable,
    onTare: () {
      _weightChar?.write('t'.codeUnits);
    },
  ),
),
```

## 3. The bug I found — two different weights

First version of the button only did maths **on the phone**:
```dart
grams: _grams - _tare,
onTare: () { setState(() { _tare = _grams; }); },
```
Result:
```
ESP32 LCD : 13.4 g      <- the scale never changed
Phone     : 0.000 kg    <- only the phone subtracted 13.4
```
**Two different weights — wrong for a weighing machine.** The customer looks at the LCD,
the shopkeeper at the phone; they must agree.

**The correct design was already in `01_PROJECT_CONTEXT.md`:**
> Properties: NOTIFY, READ, **WRITE (for tare commands from the app)**.
> **Two-way BLE:** the app reads weight AND writes tare commands back to the ESP32.

**Fix:** the button **writes `'t'` to the ESP32**; the **scale itself** tares; LCD and
phone both read 0. **One source of truth: the scale.**

```
Phone --notify-- ESP32     weight "0.0,1" about twice a second
Phone --write--> ESP32     "t" -> scale.tare() -> LCD and phone both 0.000 kg
```

## 4. Flutter side — writing to the ESP32

```dart
BluetoothCharacteristic? _weightChar;      // class body (state variable)

// in _scan(), after finding weightChar:
_weightChar = weightChar;

// the Tare button:
onTare: () {
  _weightChar?.write('t'.codeUnits);
},
```

| Code | Meaning |
|---|---|
| `BluetoothCharacteristic?` | the package's type for a characteristic; `?` = null until `_scan()` finds it |
| `_weightChar = weightChar;` | carry it from `_scan()` into the class so `build()` can reach it (scope, section 5) |
| `'t'.codeUnits` | text -> bytes: `[116]`. **Reverse of `String.fromCharCodes`.** Bluetooth carries bytes both ways |
| `.write(bytes)` | send bytes to the ESP32 (needs the WRITE property) |
| `_weightChar?.write(...)` | only if not null — tapping Tare before connecting does nothing instead of crashing |

## 5. DART CONCEPT — SCOPE (where a variable can be seen)

> **A variable declared in the class body can be seen by every function in the class.
> A variable declared inside a function can only be seen inside that function — and it
> is gone when the function ends.**

```
class _SpalshscreenState {          <- the HOUSE
  _weightChar                       <- in the HALL: every room can see it

  _scan() {                         <- ROOM 1 (kitchen)
    final weightChar = ...;         <- only inside the kitchen
  }                                 <- _scan() ends -> weightChar is GONE

  build() {                         <- ROOM 2 (shop counter)
    weightChar                      X  "Undefined name 'weightChar'"
    _weightChar                     OK
  }
}
```

**Proved by experiment:** writing `weightChar.write(...)` inside `onTare` gave a red
`Undefined name 'weightChar'`. Undone with Ctrl+Z.

**Already used without noticing:** `_grams` is changed in `_scan()` and shown in
`build()` — that only works because `_grams` lives in the class body.

- **local variable** = inside a function
- **state / field variable** = in the class body

### Other Dart used here
| Feature | Syntax | Meaning |
|---|---|---|
| `required` named parameter | `const X({required this.a})` | must be passed: `X(a: 1)`; leaving it out is an error |
| `this.` in a constructor | `required this.grams` | store the argument straight into the field `grams` |
| `final` fields | `final double grams;` | widget inputs never change after creation |
| `VoidCallback` | `final VoidCallback onTare;` | type for "a function that takes nothing and returns nothing" — `() { ... }` |
| function as an argument | `onTare: () { ... }` | hand over code to run **later**, on tap (like the Timer callback in F1.4) |
| ternary for style | `color: isStable ? green : amber` | one widget, two looks, picked by state |
| `codeUnits` | `'t'.codeUnits` | `[116]` — string -> bytes |

## 6. ESP32 side — the sketch changes

The sketch's characteristic was **READ + NOTIFY only** — the phone was not allowed to
write. Its tare only worked from the **Serial Monitor** (`t` over USB).

```
Laptop Serial Monitor --USB-------> 't' -> scale.tare()   worked already
Phone app ------------Bluetooth---> 't' -> ???             nobody was listening
```

The full sketch is now in the project: **`firmware/esp32_scale/esp32_scale.ino`**
(Arduino needs the folder and the `.ino` to share a name).

### The four changes
**1. A flag**
```cpp
volatile bool tareRequested = false;
```
**2. A write callback** (same pattern as `MyServerCallbacks`)
```cpp
class TareCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic *c) {
    String v = c->getValue().c_str();
    if (v == "t") {
      tareRequested = true;
    }
  }
};
```
**3. Allow WRITE and attach the callback** (in `setup()`)
```cpp
weightCharacteristic = service->createCharacteristic(
  CHARACTERISTIC_UUID,
  BLECharacteristic::PROPERTY_READ |
  BLECharacteristic::PROPERTY_NOTIFY |
  BLECharacteristic::PROPERTY_WRITE
);
weightCharacteristic->addDescriptor(new BLE2902());
weightCharacteristic->setCallbacks(new TareCallbacks());
```
**4. Tare from Serial OR Bluetooth** (top of `loop()`)
```cpp
bool doTare = tareRequested;
if (Serial.available() > 0 && Serial.read() == 't') {
  doTare = true;
}
if (doTare) {
  tareRequested = false;
  scale.tare(20);
  // reset stability readings ...
}
```

### Why a flag instead of calling `scale.tare()` inside `onWrite`
`onWrite` runs inside the **Bluetooth task**. `tare(20)` takes ~1.5 s (20 readings —
seen in the log: `>>> Taring...` at 26.4 s, `>>> TARED` at 27.9 s). Blocking Bluetooth
that long can drop the connection. So `onWrite` only **raises a flag**; `loop()` does the
real work on its next pass. `volatile` tells the compiler the variable can change from
another task, so it must always re-read it.

### Other facts seen
- **Uploading restarts the ESP32**, and `setup()` tares the empty scale — that is why the
  old 13 g offset disappeared after the upload.
- The sketch already clamps tiny values to 0 (`abs(grams) < 2`), so the empty pan sends
  `0.0,1`.
- After changing a characteristic's properties, **toggle the phone's Bluetooth off/on**:
  Android caches the old list of services.

## 8. GATE — PASSED

**Q: `WeightBar` is Stateless but its weight changes — how?** The splash screen's State
holds `_grams` and calls `setState`; its `build()` re-creates `WeightBar` with the new
value. WeightBar only draws what it is given.

**Q: Why was subtracting `_tare` on the phone wrong?** The phone showed 0 but the machine
did not — two different weights. Now the app writes `'t'` to the ESP32 and the scale
itself tares, so both agree.

**Q: Why copy `weightChar` into `_weightChar`?** A variable in the class body can be seen
anywhere in the class; one inside a function is seen only inside it. The Tare button is
in `build()`, so it needs the class-level one.
