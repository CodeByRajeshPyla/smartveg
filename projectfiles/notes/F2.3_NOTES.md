## 1. Future vs Stream — the one idea

| | Future | Stream |
|---|---|---|
| gives | **ONE** value, once, later | **MANY** values, one after another, no end |
| like | ordering a parcel — arrives once, done | a WhatsApp group — messages keep coming |
| how you get it | `await` | `.listen((value) { ... })` |
| in this app | `connect()`, `discoverServices()` — finish once | the weight, about twice a second, forever |

**Why no `await` before `listen`:** `await` waits until something *finishes*. A Stream
never finishes — `await` would wait forever and nothing below it would run. `listen`
just **registers** a function ("call this for every value") and returns immediately.

> **Future = an answer you wait for. Stream = a tap you leave open.**

## 2. How BLE data is organised — GATT

```
ESP32-Scale                  = the cupboard (device)
 ├── Service                 = a drawer (group of related data)
 │    └── Characteristic     = a box in the drawer (one piece of data)
 └── Service
      └── Characteristic     <- the weight "13.4,1" lives here
```
Every service and characteristic has a **UUID** (unique label).

### What `discoverServices()` found on this scale
```
SERVICE 1801                                   standard — Generic Attribute
   CHAR 2a05                                   "Service Changed"
SERVICE 1800                                   standard — Generic Access
   CHAR 2a00, 2a01, 2aa6                       Device Name, Appearance, address settings
SERVICE 12345678-1234-1234-1234-1234567890ab   CUSTOM — the scale
   CHAR abcd1234-5678-90ab-cdef-1234567890ab   CUSTOM — the weight
```
- **Short UUID (4 chars)** = official, defined by the Bluetooth standard; every device has these.
- **Long UUID (36 chars)** = custom, chosen by whoever wrote the ESP32's Arduino code.

**THE APP'S TWO UUIDS (must match the ESP32 sketch exactly):**
- service `12345678-1234-1234-1234-1234567890ab`
- weight characteristic `abcd1234-5678-90ab-cdef-1234567890ab`

The exploring code (printed every service and characteristic) — used once, to find them:
```dart
final services = await device.discoverServices();
for (final s in services) {
  print('SERVICE ${s.uuid}');
  for (final c in s.characteristics) {
    print('   CHAR ${c.uuid}');
  }
}
```

## 3. Read vs Notify

| Way | How | |
|---|---|---|
| **read** | the app asks "what is the weight?" every time | must keep asking — slow, wasteful |
| **notify** | the app says once "tell me whenever it changes"; the ESP32 **pushes** each reading | used here |

`await weightChar.setNotifyValue(true);` — switch notify on. It is a Future (the phone asks
the ESP32 and waits for "OK"), so it is awaited.
**Without it** the ESP32 never pushes anything: the stream stays silent and no weight
ever arrives.

Seen in the log, once per reading: `[FBP] onCharacteristicChanged: chr: abcd1234-...`

## 4. Bytes -> text -> values (parsing)

Bluetooth carries **bytes** (numbers), not text. Each character travels as its code number:
```
"13.4,1"  travels as  [49, 51, 46, 52, 44, 49]
                       '1' '3' '.' '4' ',' '1'
```

```
bytes [49,51,46,52,44,49]
  -> String.fromCharCodes  -> "13.4,1"
  -> split(',')            -> ["13.4", "1"]
  -> double.parse(parts[0])-> _grams = 13.4
  -> parts[1] == '1'       -> _isStable = true
```

---

## 5. The full journey of one reading — "503.0,0"

```
ESP32 sends bytes
 -> listen calls my function with them
 -> String.fromCharCodes   -> "503.0,0"
 -> split(',')             -> ["503.0", "0"]
 -> double.parse("503.0")  -> _grams = 503.0
 -> "0" == '1' is false    -> _isStable = false
 -> setState               -> Flutter marks the screen dirty
 -> build() runs again     -> screen shows "503.0 g" and "Settling..."
```
Same rule as F1.4: **change the data with `setState`; `build()` redraws from it.** The
Stream replaced the Timer as the thing that triggers `setState`.

## 6. The code

### State variables (class body)
```dart
double _grams = 0;
bool _isStable = false;
```

### In `_scan()`, after `connect`
```dart
final services = await device.discoverServices();
final service = services.firstWhere(
  (s) => s.uuid == Guid('12345678-1234-1234-1234-1234567890ab'),
);
final weightChar = service.characteristics.firstWhere(
  (c) => c.uuid == Guid('abcd1234-5678-90ab-cdef-1234567890ab'),
);
await weightChar.setNotifyValue(true);
weightChar.lastValueStream.listen((bytes) {
  final text = String.fromCharCodes(bytes);
  final parts = text.split(',');
  setState(() {
    _grams = double.parse(parts[0]);
    _isStable = parts[1] == '1';
  });
});
```

### In `build()`, inside the card
```dart
const SizedBox(height: 12),
Text('${_grams.toStringAsFixed(1)} g', style: const TextStyle(fontSize: 32)),
Text(_isStable ? 'Stable' : 'Settling...'),
```

### Line by line in plain English
| Code | Meaning |
|---|---|
| `discoverServices()` | "ESP32, list all your drawers" |
| `services.firstWhere((s) => ...)` | "take the drawer labelled 12345678..." |
| `service.characteristics.firstWhere(...)` | "from it, take the box labelled abcd1234..." |
| `setNotifyValue(true)` | "push me every new reading" |
| `lastValueStream.listen((bytes) { ... })` | "every time a reading arrives, run this" — the stream calls it, I never do |
| `String.fromCharCodes(bytes)` | bytes -> text |
| `text.split(',')` | cut at the comma |
| `double.parse(parts[0])` | text -> real number |
| `parts[1] == '1'` | true if stable |
| `setState(...)` | change the data and ask Flutter to redraw |

### Built in five visible pieces
1. print every service and characteristic -> found the UUIDs
2. `firstWhere` to pick the weight characteristic -> printed `weight char: abcd1234-...`
3. notify + listen + print -> terminal filled with `13.4,1`, twice a second
4. `setState` into `String _reading` + a `Text` -> raw `13.4,1` on the **phone**
5. parse into `double _grams` + `bool _isStable` -> `13.4 g` / `Stable`

## 7. DART CONCEPTS USED HERE

| Feature | Syntax | Meaning |
|---|---|---|
| nested for-in | `for (final s in list) { for (final c in s.items) { } }` | for each item, then for each item inside it |
| string interpolation with a dot | `'${s.uuid}'` | `${...}` needed for expressions; `$x` only for a plain name |
| `firstWhere` | `list.firstWhere((x) => test)` | first item where the test is true. **Crashes if none match.** `[3,8,12].firstWhere((n) => n > 5)` -> `8` |
| arrow function | `(s) => s.uuid == id` | small function returning one expression (true/false here) |
| `Stream<T>` | `Stream<List<int>>` | a stream whose values are lists of ints (bytes) |
| `.listen(fn)` | `stream.listen((v) { ... })` | register a function called for **every** value |
| anonymous function | `(bytes) { ... }` | no name; the stream calls it (like `Timer.periodic` in F1.4) |
| `List<int>` | `[49, 51, 46]` | list of numbers — bytes |
| `String.fromCharCodes` | `String.fromCharCodes([72, 105])` | `"Hi"` — char codes -> text |
| `split` | `"13.4,1".split(',')` | `["13.4", "1"]` |
| list index | `parts[0]` | first item — **positions start at 0** |
| `double.parse` | `double.parse("13.4")` | `13.4`. Crashes on non-numbers like `"abc"` |
| `bool` | `bool _isStable = false;` | only `true` or `false` |
| `==` produces a bool | `parts[1] == '1'` | `true` or `false` — can be assigned directly |
| `toStringAsFixed(n)` | `13.456.toStringAsFixed(1)` | `"13.5"` — number -> text with n decimals |
| multi-line comment | `/* ... */` | everything between is skipped. Single line: `//` |

`.uuid`, `Guid('...')` (the package's UUID type — compare with `==`),

## 8. What the readings showed

| Readings | Meaning |
|---|---|
| `13.3,1  13.7,1  13.4,1 ...` | pan empty, stable |
| `92.7,0 -> 503.0,0 -> 574.2,0 -> 925.0,0` | pressing — rising, not stable |

### Why the empty pan reads ~13 g, not 0 -> TARE
A load cell is never perfectly zero: the pan's own weight, the mounting, and small
electrical offsets give a starting value. Scales fix it with **tare** — store "13.4 =
zero" and subtract it from every reading. That is the TARE button on a shop scale.
Built in **F2.8**.

### Why it jumps 13.0 ... 14.0 -> NOISE -> the stable flag
The load cell measures tiny electrical changes; vibration, air movement and electrical
jitter make it wobble. That is why the ESP32 sends a **stable flag**: the app will only
let an item be added to the bill once the reading has stopped wobbling. Built in **F2.7**.

### `double` for grams is fine
Only *displayed*, rounded with `toStringAsFixed(1)`. Money stays whole-number paise in an
`int` (F1.4 rule).

## 10. GATE — PASSED

**Q: Future vs Stream?** A Future is one value later (connection done or not). A Stream
is many values continuously (the scale's weight).

**Q: What does `setNotifyValue(true)` do?** Asks the ESP32 to push every new reading.
Without it no reading ever arrives.

**Q: Why no `await` before `listen`?** The weights keep coming forever; `await` would wait
forever. `listen` registers a function and returns immediately.

**Q: What does `String.fromCharCodes` do?** Converts the bytes Bluetooth carries back into
text (`"13.4,1"`).

**Q: Journey of `"503.0,0"`?** bytes -> text -> split -> `_grams = 503.0`,
`_isStable = false` -> `setState` -> `build` -> "503.0 g" / "Settling...".

**Q: Why ~13 g and jumping?** Load-cell offset (fixed by tare) and noise (handled by the
stable flag).

## 11. How the whole app runs — in TIME order, not file order

**The file is not run top to bottom.** It is a set of methods; Flutter decides when each
one is called.

### Step 0 — the app starts (`main.dart`)
```
main()                         main.dart line 4 — the first thing Dart runs
 -> runApp(SmartvegApp())      start Flutter with my app
 -> SmartvegApp.build()        returns MaterialApp(home: Spalshscreen())
 -> Spalshscreen is Stateful   Flutter calls createState()

```

### Step 1 — `initState()` — ONCE (line 18)

### Step 2 — `build()` — the first draw (line 82)
Draws from the starting data: empty bar, "Scanning for ESP32-Scale...", `0.0 g`,

### Step 3 — two things now run side by side, each calling `setState`
| Time | Timer (line 20) | `_scan()` (line 38) |

## 12. initState, setState, build — the relation

| Method | Who calls it | When | How many times | Job |
|---|---|---|---|---|
| `initState()` | Flutter | screen is born | **once** | **start** things: timer, scan, listening |
| `build()` | Flutter | first draw, and after every `setState` | **many** | **draw** the screen from the current data |
| `setState()` | **me** | whenever data shown on screen changes | as often as needed | change the data + tell Flutter to redraw |
| `dispose()` | Flutter | screen dies | **once** | **stop** what initState started |

### How `setState` leads to `build`
```
setState(() { _grams = 503.0; })
  1. runs my code           -> _grams is now 503.0
  2. marks the screen dirty -> "this screen needs redrawing"
Flutter, on the next frame (~16 ms later)
  3. calls build()          -> build reads _grams -> draws "503.0 g"
```
**I never call `build()` myself.** `setState` is the doorbell; Flutter answers it by
calling `build`.

**Analogy:** I keep the numbers in a notebook (the state variables). The painter (Flutter)
paints the shop board (the screen) from my notebook. Changing the notebook alone does
nothing — the board stays old (proved in F1.4 without `setState`). Ringing the bell
(`setState`) makes the painter look at the notebook and repaint (`build`).

### Who rings the bell in this file
| Source | Line | Changes |
|---|---|---|
| Timer | 21 | `_ticks` |
| BLE Stream | 65 | `_grams`, `_isStable` |
| (later) button taps | | cart items, totals |

### When to use what
- Something must **start once** when the screen opens -> **`initState`**
- Data shown on screen **changed** -> wrap the change in **`setState`**
- **Describe** what the screen looks like -> **`build`** (only drawing: never start timers
  or call `setState` inside it)
- Something must **stop** when the screen closes -> **`dispose`**

> **Open once (`initState`), change data with `setState`, Flutter redraws with `build`,
> close once (`dispose`).**
